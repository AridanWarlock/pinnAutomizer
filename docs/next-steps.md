Аудит PR #16, принятого 18 октября 2026 года; TASK-3 продолжается небольшими PR.
Runtime solver подключён; ниже отмечены проверенные механизмы и оставшиеся ограничения.

## Исправлено при повторной проверке

| Дефект PR | Воспроизведение | Исправление и предел гарантии |
| --- | --- | --- |

Тест сохраняет схему/историю. Изменение содержимого файла с тем же номером без checksum этим не выявляется |

Сначала регрессионные тесты упали на исходном коде, затем прошли после исправлений.
Это сильнее теста, написанного только под уже исправленную реализацию: известно,
какое наблюдаемое поведение он защищает.

Проверены `make fmt`, полный `make check` с отдельным временным PostgreSQL и
адресные `-race` для общего SQLite-клиента и solver SQLite-адаптера. Полный check
включает тесты пяти модулей, runner и закреплённый линтер. Это не сквозной запуск
распределённой системы. В этом аудите не запускались Docker/Kafka/Redis-интеграции,
PINN, миграции рабочей БД или deploy. Тестовый PostgreSQL после проверок остановлен.

## Известные ограничения вне этих исправлений

### Дополнение после review 17 октября

Domain/core отделены от входных данных: `Attempt.Validate`, проверяемое восстановление,
методы переходов, конструкторы `Event` и `KafkaMessage`, валидируемый `Input`.
Конструкторы KafkaMessage теперь возвращают ошибку; все вызовы согласованы.
Экспортируемые поля legacy-моделей пока защищены конвенцией, а не компилятором.
Положительный `limit.Limit` имеет закрытое поле; нулевое значение отклоняется.

SQLite-адаптер разделён на конструктор, запросы attempts/outbox и row-конверторы.
Использует мокируемый shared-клиент, UUID как driver.Valuer, именованные SQL-колонки,
INSERT RETURNING и транзакционную проверку повторной регистрации. Время по-прежнему
хранится INTEGER nanoseconds, но Scan/Value реализует общий `sqlite.SQLTime`.

Solver outbox отправляет batch и удаляет подтверждённые ID одним SQL-запросом.
Потерянное подтверждение допускает повтор; совместимость tasks outbox с обёрнутыми
ошибками драйвера сохранена через errors.As. Смена доставки runtime solver всё ещё
не выполнялась. IDE ignore восстановлен; ошибочное правило для каталога docker удалено.

В этом раунде доступны и проверены изолированные Docker-интеграции:

- PostgreSQL: существующие транзакционные тесты tasks в полном `make check`.
- Kafka: batch в две темы, key/value/headers. Опция тестов — `PINN_TEST_KAFKA_ADDR`.
- Goose: настоящий image, Up/reopen, отклонение при Linux ownership lock и повторный Up.
  Опция — `PINN_TEST_DOCKER=1`. Образ уже содержит flock, отдельная сборка убрана.
- SQLite в Linux-контейнере: конкуренция, rollback/reopen, intent и SIGKILL владельца.

Новые Docker-интеграции включаются явно; текущий CI автоматически поднимает только
PostgreSQL. PINN, GPU, power loss и восстановление Docker-вычисления эти проверки
не охватывают. Контейнеры тестов не используют рабочие volume-ы.

### Оставшиеся ограничения

| Наблюдение в исходниках | Последствие | Следующая проверка / действие |
| --- | --- | --- |
| Runtime solver использует durable accept/recovery/outbox | Неопределённый Start удерживает слот; потеря журнала не восстанавливается из Docker автоматически | Проверить PINN/GPU и отдельно определить ручной разбор неизвестного исхода |
| Прежний Docker runner использует AutoRemove, нет явного Stop при timeout; log goroutine не ожидается владельцем | Нельзя надёжно восстановить exit code; timeout ожидания не останавливает контейнер | Короткий CPU-контейнер и fault injection при Create/Start/Wait; PINN не нужен |
| `tasks/create` использует устойчивое задание очистки до файлового I/O | Незавершённые загрузки очищаются; POST пока без idempotency key | TASK-16: проверить recovery и короткий commit; NFS/power loss остаются вне гарантии |
| tasks outbox публикует в Kafka под SQL-транзакцией | Задержка брокера удерживает соединение и locks; несколько отправителей усложняют порядок | Проверить поведение с недоступным брокером и наблюдать возраст outbox; выделять claim/publish/ack только при обоснованной необходимости |
| Gateway читает Redis на каждом защищённом запросе без L1 | DEL/expiry дают 401, сбой backend даёт 503 | TASK-19: гарантия и проверки в [session-auth.md](session-auth.md); гонки refresh/logout остаются следующим этапом |
| TASK-18: poolx закрывает pool при ошибке Ping и привязывает tx к клиенту | Разные клиенты сохраняют независимость commit/rollback; вложенность одного клиента явно отклоняется | Проверки и пределы гарантии описаны в [postgres-pool.md](postgres-pool.md) |
| Compromised-session consumer auth тоже at-most-once | Ошибка обработки может потерять уведомление об отзыве | Проверить повторяемость сценария и публикацию заголовков до смены стратегии |

Это выводы из кода и возможные последствия, а не отчёт о сбоях в production.
Изменения этих механизмов не включены незаметно в чистку SQLite.

## Предлагаемая очередь небольших изменений

1. **PR #16 принят.** SQLite ledger, accept и outbox подготовлены; runtime ещё прежний.
2. **TASK-3: безопасные Docker-операции.** Добавлены отдельный `tasks/start` и методы
   PinnRunner для Create/Inspect/Start. Стабильное имя и labels связывают контейнер
   с run_id/task_id/mode; AutoRemove и автоматический restart для нового пути отключены.
   Только победитель устойчивого RequestStart отправляет Start. Потерянный ответ
   сверяется через Inspect с отдельным timeout; недоступный Docker не считается
   отсутствующим контейнером. Повтор Start запрещён, включая переоткрытие журнала.
   Сбой после записи намерения до отправки Start может оставить вычисление незапущенным:
   безопасное восстановление — следующий PR. Параметры image/name должны сохраняться
   для незавершённых попыток. Ручное удаление контейнеров и потеря журнала не покрываются.
   Проверки: unit fault injection Create/Start/cancel, конкуренция с SQLite на диске
   и короткий Docker CPU-контейнер. Usecase подключён к cmd/main.go через recovery.
3. **TASK-3: наблюдение и завершение.** tasks/observe сохраняет подтверждённый
   результат exited-контейнера и outbox; повторы/конкуренция/rollback/reopen проверяются
   отдельно. Подготовлены tasks/recover и worker начального/периодического обхода:
   keyset-страницы, продвижение мимо ошибок, timeout на попытку, без повторного Start
   после intent. Deadline и подтверждённый Stop подготовлены
   в ObserveAttempt. Подготовлен cleanup с durable cleaned_at и повтором удаления
   после сбоя; recovery подбирает finished без маркера. Runtime подключён в #24.
4. **TASK-3: runtime и эксплуатационные ограничения.** Подключены journal,
   accept consumer at-least-once, recovery и outbox под lifecycle; лимит активных
   попыток резервируется в SQLite. Аварийный перезапуск проверяется дочерними
   процессами с Process.Kill и CPU-контейнером; порядок диагностики описан в
   [solver-recovery.md](solver-recovery.md). Неопределённый Start удерживает слот;
   операторская отмена — отдельное решение. Реальный PINN API отложен до его
   стабилизации, исправления остальных проблем, общего рефакторинга и расширенного
   тестирования. CPU smoke не доказывает GPU-поведение или математический результат.
   Старые сообщения и данные поддерживать не требуется.
5. **Загрузка файлов.** Удаление задачи и durable очередь очистки подготовлены
   в TASK-15; семантика описана в [task-file-cleanup.md](task-file-cleanup.md).
   В TASK-16 tasks/create пишет файлы вне транзакции; устойчивое задание и файловая
   блокировка защищают очистку после сбоя. Владение poolx исправляется отдельно в TASK-18.
6. **Сессии auth/gateway.** TASK-19 убирает L1 из авторизации и разделяет 401/503
   по согласованной гарантии. Далее — конкуренция refresh/logout и частичный сбой
   PostgreSQL/Redis.
   Не обещать атомарность между двумя хранилищами.
7. **TASK-8: обновления ПО.** Проверять закреплённые версии в go.mod, Dockerfiles,
   Compose и CI. TASK-8.2 выравнивает Go на 1.27.3; детали —
   [go-toolchain.md](go-toolchain.md).
   Целевые версии и совместимость, включая заявленный в TASK-8.1 стандартный UUID,
   нужно заново проверить по официальным источникам при взятии задачи. Название
   backlog-задачи само по себе не является подтверждением доступного API.

Для нового этапа после принятия PR — ветка от актуальной `codex/task-progress`,
одна гарантия на PR и конкретное доказательство её проверки. Новые механизмы
масштабирования не нужны до появления ограничений текущего размещения.

## Минимальная эксплуатационная обратная связь

После восстановления исполнения стоит добавить наблюдение за возрастом старейшего
outbox-события, числом незавершённых попыток, ошибками Docker, временем ожидания
в очереди и размером SQLite/WAL. Сам по себе успешный HTTP health check не показывает,
что задачи продвигаются. Порогам и реакции оператора нужна конкретная цель сервиса;
добавлять новый стек мониторинга в этот PR ради этих предложений не требуется.
