распределённой системы. В этом аудите не запускались Docker/Kafka/Redis-интеграции,
PINN, миграции рабочей БД или deploy. Тестовый PostgreSQL после проверок остановлен.

## Известные ограничения вне этих исправлений

| Наблюдение в исходниках | Последствие | Следующая проверка / действие |
| --- | --- | --- |
| SQLite/accept/outbox solver не подключены; runtime at-most-once | Остановка после подтверждения Kafka может потерять вычисление | Завершить TASK-3, затем отдельно включать новый путь |
| Прежний Docker runner использует AutoRemove, нет явного Stop при timeout; log goroutine не ожидается владельцем | Нельзя надёжно восстановить exit code; timeout ожидания не останавливает контейнер | Короткий CPU-контейнер и fault injection при Create/Start/Wait; PINN не нужен |
| `tasks/create` держит транзакцию при записи файлов; `delete` после commit только логирует ошибки очистки | Долгие блокировки/осиротевшие файлы после сбоя | Отдельный сценарий staging/подтверждения файлов и устойчивой очистки, без переноса I/O в SQL-адаптер |
| tasks outbox публикует в Kafka под SQL-транзакцией | Задержка брокера удерживает соединение и locks; несколько отправителей усложняют порядок | Проверить поведение с недоступным брокером и наблюдать возраст outbox; выделять claim/publish/ack только при обоснованной необходимости |
| Gateway L1 кеширует сессию на 30 секунд независимо от остаточного TTL Redis; logout другого процесса L1 не очищает | Отзыв сессии может быть виден с задержкой; требования к задержке отзыва пока не зафиксированы | Сначала согласовать гарантию отзыва; затем проверить logout/refresh/expiry через gateway с реальным Redis |
| `poolx.New` не закрывает созданный pool при неуспешном Ping; context-транзакция poolx не привязана к клиенту | При ошибке инициализации возможен ресурсный leak; несколько pool-клиентов в одном context небезопасны | Отдельное небольшое исправление с проверкой владения ресурсами; не копировать этот код в SQLite |
| Compromised-session consumer auth тоже at-most-once | Ошибка обработки может потерять уведомление об отзыве | Проверить повторяемость сценария и публикацию заголовков до смены стратегии |

Это выводы из кода и возможные последствия, а не отчёт о сбоях в production.
Изменения этих механизмов не включены незаметно в чистку SQLite.

## Предлагаемая очередь небольших изменений

1. **Завершить review PR #16.** Обсудить границы ledger и SQL API. Не сливать ветку
   и не менять семантику доставки до решения пользователя. Аудит добавлен в тот же
   PR, потому что проверяет и исправляет его код.
2. **TASK-3: безопасные Docker-операции.** Отдельный PR с детерминированным именем,
   Inspect и обработкой потерянного ответа Create/Start. Критерий: повтор одной
   попытки не вызывает второе вычисление; любой неопределённый исход диагностируется.
   Общую запись intent нельзя держать открытой во время Docker I/O.
3. **TASK-3: восстановление и завершение.** Следующий PR: существующий running
   контейнер наблюдается, exited даёт устойчивый итог + outbox, deadline вызывает
   ограниченную остановку/очистку. Проверять перезапуск процесса между эффектами.
4. **TASK-3: включение runtime.** После предыдущих проверок подключить ledger,
   accept, recovery и outbox под lifecycle; затем переключить consumer на
   at-least-once. Отдельно описать старые сообщения без run ID и существующие
   контейнеры. До переключения нужен review и настоящая Docker/Kafka-проверка.
5. **Загрузка и очистка файлов.** Вынести долгий I/O из транзакции, сохранить
   возможность восстановить/очистить частично созданные данные. Договориться,
   когда HTTP-операция считается завершённой при сбое cleanup.
6. **Сессии auth/gateway и poolx.** Разделить на маленькие задачи: lifecycle pool,
   гарантия отзыва, затем конкуренция refresh и частичный сбой PostgreSQL/Redis.
   Не обещать атомарность между двумя хранилищами.
7. **TASK-8: обновления ПО.** Проверять закреплённые версии в go.mod, Dockerfiles,
   Compose и CI. Например, go.work уже использует 1.26.2, builder-образы — 1.26.1.
   Целевые версии и совместимость, включая заявленный в TASK-8.1 стандартный UUID,
   нужно заново проверить по официальным источникам при взятии задачи. Название
   backlog-задачи само по себе не является подтверждением доступного API.

Для нового этапа после принятия PR — ветка от актуальной `codex/task-progress`,
одна гарантия на PR и конкретное доказательство её проверки. Новые механизмы
масштабирования не нужны до появления ограничений текущего размещения.
