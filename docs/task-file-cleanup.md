# Удаление задачи и её файлов

DELETE задачи подтверждает логическое удаление и устойчивое принятие очистки.
Повтор удаления уже отсутствующей задачи тоже успешен и не создаёт новое задание.
Поиск ограничен пользователем: чужая задача при таком no-op не изменяется. Файлы удаляются в фоне: нормальный интервал между порциями
worker — 5 секунд, при ошибке файловой системы физическое удаление задерживается.

В одной PostgreSQL-транзакции usecase блокирует задачу, проверяет CanDelete,
сохраняет file_cleanup с двумя путями и удаляет task. Откат сохраняет задачу и
не оставляет задание очистки. У file_cleanup нет FK на удаляемую task: запись
должна пережить её удаление. Новая Up-миграция применяется до запуска обновлённого
сервиса, как остальные миграции tasks; runtime сам её не применяет.

Отдельный tasks/cleanup читает задания порциями по 32 через UUID cursor. RemoveAll
выполняется вне SQL-транзакции. Подтверждение удаляет задание только после успешной
очистки обоих каталогов. Отсутствующий каталог считается успешным повтором.
Частичный сбой или остановка между файловым эффектом и подтверждением сохраняют
задание для следующего обхода. Ошибочное задание не блокирует следующие страницы;
новые строки перед cursor обрабатываются в следующем обходе. Пустая страница
сбрасывает cursor в UUID Nil: сохранённые ошибочные задания читаются заново.

Два worker могут прочитать одно задание. Перед удалением worker захватывает общую
файловую блокировку и перепроверяет наличие задания в PostgreSQL. Устаревшая выборка
после успешного создания задачи не разрешает удалять её файлы. Короткий SELECT FOR
UPDATE NOWAIT откладывает очистку при незавершённом commit/rollback: ошибка блокировки
означает повтор в следующем обходе. Обычный MVCC SELECT мог бы прочитать старую строку. SQL-блокировка освобождается до файлового I/O; запрос ограничен timeout клиента.
Повтор RemoveAll и ACK допустимы. Task ID и каталоги не переиспользуются.
Сущность FileCleanupJob создаётся проверяющим конструктором. Поля экспортируются по принятой
конвенции domain; вызывающий код не должен их изменять. Проверяются абсолютные разные пути с конечным каталогом task_id;
это защита от ошибочного удаления корневого/чужого каталога, а не filesystem sandbox.

Worker участвует в lifecycle tasks и завершается до закрытия PostgreSQL.
Общий pkg/worker выполняет последовательный цикл, задержку и логирование ошибок;
сервисный process-метод и поле worker хранят cursor. Тот же механизм используется solver recovery.
Отмена проверяется между операциями, без WithoutCancel. Уже начатый os.RemoveAll
контекстом не прерывается; остановка процесса также оставляет задание для повтора.

Все worker должны видеть тот же volume с файлами. Обработка локальных дисков
нескольких независимых hosts потребует отдельного назначения владельца данных.
Сканирование старых orphan-каталогов не выполняется.

## Создание задачи

Создание сначала захватывает ту же файловую блокировку и сохраняет file_cleanup
отдельным commit, до создания каталогов и записи файлов. Затем пишет файлы вне SQL-
транзакции. После успешной записи короткая транзакция создаёт task и удаляет cleanup.
Незавершённая задача не видна GET/run. Ошибка записи, rollback или убийство процесса
оставляют cleanup; worker удалит частичные данные после освобождения блокировки ОС.
При неизвестном результате commit синхронной компенсации нет: worker сначала
проверяет устойчивый результат в БД, чтобы не удалить файлы успешно созданной задачи.

Shared pkg/filelock использует advisory flock (Linux/macOS). В корне data volume
лежат максимум 256 постоянных .files-XX.lock; shard выбран обычным FNV-1a хешем имени каталога по модулю 256.
Криптографическая стойкость здесь не требуется: хеш только распределяет блокировки. Коллизия даёт
конфликт и повтор позже, а не параллельный доступ к тем же файлам. Lock-файлы нельзя
удалять: иначе процессы могут захватить разные inode. Долгая запись удерживает только
filesystem lock, без занятого SQL-соединения. Нужен общий volume с корректной flock-
семантикой; NFS и другие сетевые FS отдельно не проверены. При обновлении нельзя
оставлять старые workers, которые не используют блокировки.

POST создания пока не имеет idempotency key: повтор после потерянного HTTP-ответа
может создать вторую задачу. Повторять байтовую загрузку после сбоя нечем — входные
данные остаются у клиента; сервер очищает незавершённое создание. Power loss и fsync-
гарантии не проверены. Отмена проверяется инфраструктурой при захвате lock и выполнении SQL; уже начатый
io.Copy, как и RemoveAll, не прерывается контекстом.

Проверки создания: fault injection по стадиям, отсутствие SQL-транзакции при записи,
конкурентная очистка, устаревшая выборка, отложенную проверку незавершённого commit/rollback и убийство отдельного
процесса с последующей очисткой. Дочерний процесс использует только одноразовую БД
и временный файловый volume.

Проверки включают настоящий PostgreSQL и временные каталоги: rollback удаления,
частичный отказ файлов, отказ подтверждения после физического удаления, reopen,
повтор и конкурирующие worker. Моки проверяют cursor, отмену и порядок операций;
они не заменяют SQL-интеграции.
