# Ротация refresh-токена

Runtime: auth `cmd/main.go` → `authRefresh` → PostgreSQL и Redis.
PostgreSQL хранит hash refresh-секрета и JTI; Redis — сессию access-токена.
Контракт Input/Output не изменён, срок refresh при ротации не продлевается.

## Порядок эффектов

1. Проверить вход, fingerprint, срок refresh и получить роли.
2. Создать новый access/JTI и сохранить Redis-сессию кандидата с существующим TTL
   access-токена (15 минут). Клиент ещё не знает его токенов.
3. Удалить старую Redis-сессию по JTI прочитанного refresh; отсутствие допустимо.
4. Выполнить условный UPDATE PostgreSQL по старому hash.
5. Только победитель UPDATE получает новую пару токенов.

Ошибка SET или DEL возвращает 503 до SQL-ротации: сама ошибка Redis не потребляет
известный клиенту refresh-секрет. HTTP handler не заменяет cookie при ошибке.
Повтор возможен, пока другой запрос/logout не изменил запись. При неизвестном
исходе DEL старый access уже мог потерять сессию; его сохранность не обещается.

Ноль изменённых SQL-строк — штатный конкурентный проигрыш (401).
Проигравший удаляет только собственный JTI кандидата, а не JTI победителя.
Классификацию недоступности выполняет Redis-адаптер, включая сеть, отмену, закрытие
клиента и исчерпание пула; ошибки JSON остаются внутренними ошибками.
Если очистка кандидата недоступна, HTTP возвращает 503 (приоритет инфраструктурной
ошибки), сохраняя также причину конкурентного проигрыша в цепочке.
Ошибка этой очистки сохраняется в цепочке ошибок; кандидат остаётся до TTL.
Также до TTL могут оставаться кандидаты после SET с потерянным ответом,
неуспешного DEL или остановки процесса. Эти токены клиенту не выдавались.

## Пределы

Это не атомарная операция PostgreSQL/Redis. При SQL-ошибке commit мог состояться:
кандидата удалять нельзя, иначе можно уничтожить уже действующую сессию.
Если SQL commit или успешный HTTP-ответ потерян, клиент не знает новый refresh,
а старый уже израсходован. Текущий API требует повторного входа; устойчивое
восстановление ответа потребует отдельного согласованного контракта идемпотентности.
Гонки с logout/новым login в этом изменении не устранены.

## Проверки

Unit-тест сначала воспроизвёл потерю refresh при отказе Redis на прежнем порядке.
Интеграционные тесты в auth PostgreSQL-адаптере используют отдельную временную БД
и собственные Redis-ключи: SET до/после эффекта, повтор, два синхронизированных
refresh и SQL-ответ, потерянный после реального commit. Для запуска нужны
`PINN_TEST_POSTGRES_DSN` и `PINN_TEST_REDIS_ADDR`; без них тесты пропускаются.
