# Разбор восстановления solver

Реальный PINN API пока нестабилен. Аварийные сценарии проверяются коротким CPU
контейнером; эти проверки не подтверждают математический результат или GPU.

## После остановки процесса

Контейнер и запись попытки живут дольше процесса solver. После старта с тем же
journal volume recovery читает попытки, а не запускает вычисление заново:

- registered/created: подготовка и первая попытка RequestStart;
- start_requested/running: только Inspect, наблюдение deadline и при необходимости Stop;
- finished без cleaned_at: только повторяемая очистка;
- finished с cleaned_at: работа закончена.

Лимит слотов считает start_requested/running. Неизвестный исход Start тоже занимает
слот: иначе один недоступный Docker мог бы привести к запуску многих вычислений.

## С чего начать диагностику

Ошибка recovery содержит run ID, состояние и container ID снимка журнала,
прочитанного в начале обработки. Снимок может отставать от выполненного перехода;
это не утверждение о текущем состоянии Docker. Следующая ошибка содержит
исходную причину Inspect/Start/Stop или SQL I/O.

Для выбранного run ID прочитать запись SQLite в режиме read-only:

```sql
SELECT run_id, task_id, state, container_id, deadline, completed_at, cleaned_at
FROM attempts
WHERE run_id = '<run-id>';
```

Для найденного container ID получить только нужные поля, без env:

```sh
docker inspect --format '{{.Id}} {{.Name}} {{json .State}} {{json .Config.Labels}} {{.Config.Image}} {{.HostConfig.AutoRemove}} {{.HostConfig.RestartPolicy.Name}}' <container-id>
```

Сверить имя с настроенным prefix и run ID, labels pinn.solver.run_id/task_id/mode
с записью журнала, image и restart/auto-remove настройки с конфигурацией адаптера.
Проверить доступность Docker и сообщения recovery. До дальнейшего действия
сохранить диагностику: после cleanup контейнера Inspect уже не покажет его результат.

## Как понимать результат

| Наблюдение | Что разрешено заключить |
| --- | --- |
| running | Контейнер выполняется; recovery наблюдает его и ограничивает deadline |
| exited с временем запуска/завершения | Есть результат; recovery сохранит его и outbox, затем очистит контейнер |
| created и start_requested в журнале | Исход Start неизвестен: процесс мог умереть до вызова, либо запрос ещё выполнялся |
| NotFound после start_requested | Результат потерян/неизвестен; само отсутствие не доказывает успех или ошибку вычисления |
| Docker недоступен или labels отличаются | Сначала восстановить доступ/разобрать принадлежность; не менять бизнес-итог по догадке |

Нельзя вручную повторять docker start, очищать intent в SQL или удалять журнал
ради освобождения слота: завершившийся контейнер можно запустить второй раз.
Два одинаковых Inspect(created) и истечение timeout не являются доказательством,
что первоначальный Start больше не выполнится.

## Отложенное решение: операторская отмена

Сейчас автоматического abort неизвестной попытки нет. Следующий отдельный сценарий
может отменять её явной командой оператора: сначала гарантированно устранить
возможность старта прежнего container ID, затем сохранить итог отмены и outbox.
Удаление без Force должно отказывать для неожиданного running, а сбой между
внешним эффектом и записью должен допускать повтор. Политика остановки реально
работающего вычисления и смысл результата отмены требуют отдельного решения;
прямое редактирование SQL их не заменяет.

## Воспроизводимая проверка

```sh
PINN_TEST_DOCKER=1 make test TEST_ARGS='-race -count=1 -run TestRecoverySurvivesProcessKillWithoutRestartingContainerIntegration ./services/solver/cmd'
```

Нужен доступный Docker и CPU-образ golang:1.26.1-alpine
(либо PINN_TEST_DOCKER_IMAGE с sh/sleep). Проверка убивает дочерний recovery-процесс
через Process.Kill, проверяет продолжение контейнера и освобождение ownership lock,
запускает второй процесс, затем завершает тестовую CPU-команду. Проверяются прежний
StartedAt, итог, два устойчивых события, cleanup и replay. Kafka здесь не участвует:
доставка событий отдельно проверена runtime smoke-тестом с настоящим брокером.
