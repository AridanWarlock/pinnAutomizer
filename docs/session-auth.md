# Авторизация и отзыв сессии

## Согласованная гарантия

Gateway проверяет Redis на каждом защищённом запросе, без L1. Если чтение текущего
JTI началось после успешного DEL в Redis, сессия не разрешает доступ: HTTP 401.
Проверка, прочитавшая сессию до DEL, может завершиться позже; уже авторизованные
запросы не прерываются. Публичные endpoints не требуют Redis-проверки.

Ошибка Redis запрещает новый защищённый запрос с HTTP 503. Отсутствующая сессия,
неверный JWT и отсутствие bearer token дают 401. Сбой инфраструктуры не должен
заставлять клиента считать свои credentials неверными. Предполагается чтение с
актуального Redis primary, где выполнен DEL; failover с потерей подтверждённых
записей здесь не проверен.

Цена решения — одно Redis GET на защищённый запрос и зависимость доступности
авторизации от Redis. Для текущего масштаба это проще согласованной инвалидации
локальных кешей нескольких gateway. Shared CacheAside для других сценариев не менялся.

## Срок и граница logout

Login/refresh сохраняют RedisSession с TTL 15 минут. Текущий JWT не содержит exp:
Claims.GetExpirationTime возвращает nil. Срок доступа определяется наличием сессии
в Redis; изменение JWT-контракта в этот этап не входит.

Logout фиксирует отзыв до Redis I/O через атомарный метод PostgreSQL-адаптера
`RevokeSessions`; usecase затем завершает Redis-очистку:

1. В транзакции PostgreSQL читает актуальный JTI по user/fingerprint с `FOR UPDATE`.
2. Записывает в `session_revocations` актуальный JTI и JTI авторизованного запроса,
   удаляет refresh-запись и делает commit. Эти изменения атомарны в PostgreSQL.
3. После подтверждённого commit выполняет Redis DEL и удаляет подтверждённые задания.
   Отсутствующий Redis-ключ и повторное подтверждение допустимы.

Если refresh успел выполнить CAS первым, в очередь попадает его JTI. Если logout
захватил строку первым, CAS после удаления строки проигрывает и не выдаёт токены.
Ответ конкурентного refresh может дойти после logout с уже отозванным access.

**После commit отзыва refresh больше не восстанавливает авторизацию**, даже если
Redis DEL, подтверждение удаления или сам запрос завершились ошибкой/отменой.
Ошибка PostgreSQL до commit откатывает и очередь, и удаление refresh; Redis при
этом ещё не трогали. Если ответ commit потерян, исход неизвестен: committed очередь
подхватит worker, а при rollback прежняя сессия остаётся. Объявлять logout успешным
до подтверждения нельзя.

Повтор logout читает все незавершённые задания данного user/fingerprint, включая
JTI конкурентного refresh из предыдущей попытки. HTTP-повтор с уже отозванным access
может получить 401 на gateway, но очередь не зависит от повторного запроса клиента.

`cleanupSessions` и подключённый в auth `cmd/main.go` worker выполняют повтор:
DEL → подтверждение в PostgreSQL. Новый экземпляр читает очередь из БД; ошибку
подтверждения можно пережить повторным DEL. Одновременные обработчики безопасны:
JTI не переиспользуется, DEL и удаление задания идемпотентны. Курсор `*core.Jti` (`nil` — начало обхода) проходит
мимо ошибок и сбрасывается после пустой страницы, чтобы вернуться к ранним заданиям.
Выборка JTI конкретного user/fingerprint выполняется без limit — logout должен
обработать все его pending задания. Пачка фонового обхода — до 100 записей. `AUTH_SESSION_REVOCATION_INTERVAL` — 1s,
`AUTH_SESSION_REVOCATION_TIMEOUT` — 5s по умолчанию; дополнительно действуют сетевые
таймауты Redis. Общий lifecycle отменяет и дожидается worker до закрытия зависимостей.

Redis I/O больше не удерживает SQL-транзакцию. Цена — отдельная таблица и фоновый
повтор. При недоступности Redis старый access может работать до очистки или TTL;
проверка только Redis на gateway не умеет немедленно увидеть отзыв в PostgreSQL.
204 возвращается после подтверждённой очистки прочитанных заданий; при ошибке
возвращается отказ, но committed отзыв refresh не откатывается. Это не exactly-once
и не гарантия выполнения при постоянной недоступности инфраструктуры.

Новый login с корректными учётными данными может создать новую сессию; гонки с login
остаются отдельной задачей. Уже авторизованные запросы могут завершиться. Гарантия
требует обновлённых auth и gateway без L1. Исторические бесхозные JTI, которых нет
ни в запросе, ни в refresh-записи/очереди, здесь не перечисляются.

Перед запуском обновлённого auth применить новую Up-миграцию штатным Goose/make.
Runtime её не применяет. Проверок схемы в конструкторе auth PostgreSQL-адаптера нет.

## Воспроизведение и проверки

До исправления реальный Redis уже возвращал ErrKeyNotFound после DEL и естественного
TTL expiry, а прогретый CacheAside продолжал отдавать сессию. Закрытый Redis-клиент
тоже не замечался при попадании в L1. Кешировал именно runtime gateway cmd/main.go.

Unit-тесты проверяют повторное чтение Redis, 401/503 и публичные/неверные запросы.
Интеграции с двумя независимыми Redis-клиентами gateway проверяют отзыв через третий
клиент, естественное истечение TTL и HTTP 503 после разрыва настоящих TCP-соединений.
Proxy теста обрывает только собственные соединения, не останавливает общий Redis.
Тесты создают уникальные JTI и удаляют только свои ключи, без FLUSHDB.

Интеграции включаются через PINN_TEST_REDIS_ADDR (одноразовый Redis без пароля).
CI поднимает такой Redis отдельно; без env интеграции пропускаются. Это тесты
middleware с настоящим parser/Redis, а не запуск всего gateway с Kafka/auth/tasks.


Logout проверяется отдельно: оба порядка refresh/logout, Redis DEL до/после эффекта,
отмена после commit, rollback до commit, потерянный ответ реального commit,
подбор заданий новым экземпляром очистки, повтор logout с уже удалённой refresh-записью,
SQL scope/keyset и повтор подтверждения. Unit-тесты покрывают ошибку подтверждения,
обход неудачного ключа, курсор, отмену и deadline пачки. Это не Process.Kill-тест auth
и не проверка падения/потери данных самих PostgreSQL/Redis.
