# Авторизация и отзыв сессии

## Согласованная гарантия

Gateway проверяет Redis на каждом защищённом запросе, без L1. Если чтение текущего
JTI началось после успешного DEL в Redis, сессия не разрешает доступ: HTTP 401.
Проверка, прочитавшая сессию до DEL, может завершиться позже; уже авторизованные
запросы не прерываются. Публичные endpoints не требуют Redis-проверки.

Ошибка Redis запрещает новый защищённый запрос с HTTP 503. Отсутствующая сессия,
неверный JWT и отсутствие bearer token дают 401. Сбой инфраструктуры не должен
заставлять клиента считать свои credentials неверными. Предполагается чтение с
актуального Redis primary, где выполнен DEL; failover с потерей подтверждённых
записей здесь не проверен.

Цена решения — одно Redis GET на защищённый запрос и зависимость доступности
авторизации от Redis. Для текущего масштаба это проще согласованной инвалидации
локальных кешей нескольких gateway. Shared CacheAside для других сценариев не менялся.

## Срок и граница logout

Login/refresh сохраняют RedisSession с TTL 15 минут. Текущий JWT не содержит exp:
Claims.GetExpirationTime возвращает nil. Срок доступа определяется наличием сессии
в Redis; изменение JWT-контракта в этот этап не входит.

Logout удаляет текущий JTI из Redis, затем refresh token по user/fingerprint из
PostgreSQL. Проверка отзыва в этом PR покрывает эффект DEL через отдельный клиент.
Она не обещает атомарности logout между Redis/PostgreSQL, отзыва всех JTI пользователя
или защиты от конкурентного refresh, способного создать новый JTI. Это следующий
отдельный сценарий. Гарантия предполагает обновление всех экземпляров gateway:
старый экземпляр с L1 продолжит применять прежнее поведение.

## Воспроизведение и проверки

До исправления реальный Redis уже возвращал ErrKeyNotFound после DEL и естественного
TTL expiry, а прогретый CacheAside продолжал отдавать сессию. Закрытый Redis-клиент
тоже не замечался при попадании в L1. Кешировал именно runtime gateway cmd/main.go.

Unit-тесты проверяют повторное чтение Redis, 401/503 и публичные/неверные запросы.
Интеграции с двумя независимыми Redis-клиентами gateway проверяют отзыв через третий
клиент, естественное истечение TTL и HTTP 503 после разрыва настоящих TCP-соединений.
Proxy теста обрывает только собственные соединения, не останавливает общий Redis.
Тесты создают уникальные JTI и удаляют только свои ключи, без FLUSHDB.

Интеграции включаются через PINN_TEST_REDIS_ADDR (одноразовый Redis без пароля).
CI поднимает такой Redis отдельно; без env интеграции пропускаются. Это тесты
middleware с настоящим parser/Redis, а не запуск всего gateway с Kafka/auth/tasks.
