# Как понимать требования review

Основание — обсуждения пользователя и PR #16. Это объяснение принятых ограничений;
операционные правила и команды находятся в корневом `AGENTS.md`. Новые предложения
ниже не считаются автоматически согласованными изменениями архитектуры.

## Сначала конкретный сценарий, затем механизм

Хорошее обоснование начинается с наблюдаемого сбоя: «процесс умер после Docker
Start, но до записи результата». Из него следуют устойчивое намерение запуска,
Inspect и запрет слепого второго Start. Фраза «для production нужен PostgreSQL»
не объясняет, какая гарантия отсутствует у SQLite в нашем размещении.

На текущем масштабе важнее закрыть потерю команды и восстановление на том же host.
Общее хранилище для многих Docker-host, распределённые leases и fencing — отдельное
решение, когда появится такая потребность. Его нельзя незаметно добавить под видом
чистки кода.

## Почему замечания о стиле относятся к архитектуре

| Замечание | Какой принцип за ним стоит | Как проверить изменение |
| --- | --- | --- |
| `SQLite`/`Postgres`, а не общий `Repository` в DI | Название сообщает фактическую зависимость; узкий интерфейс задаёт потребности сценария | Интерфейс у потребителя, SQL и драйвер остаются в адаптере |
| `Getx/Selectx/Execx` и `Sqlizer` | Общий клиент берёт на себя протокол БД, сервис пишет свои запросы привычным способом | В solver нет ручного Scan/разбора driver errors; реальные SQL-тесты |
| Отдельные usecase-ы | Одна бизнес-цель имеет понятную точку входа | Polling, timer, логирование повторов находятся в worker |
| `defer` и приватные этапы конструктора | Видно владение ресурсом и поведение при частичной инициализации | Ошибка на любом этапе освобождает предыдущие ресурсы |
| Миграции как у остальных сервисов | Один способ доставки и эксплуатации уменьшает неожиданности | Внешний Up; runtime только проверяет; applied SQL не редактируется |
| Именованные параметры/константы, обычные переносы | Читателю не нужно угадывать смысл числа или распаковывать плотный код | `limit`, размер batch, лимит body и memory threshold имеют разные понятные имена |
| Общая рекурсивная Mockery-конфигурация | Генерация воспроизводима для всего монорепозитория | Версия закреплена, моки в Git вместе с изменившимся интерфейсом |
| Абстрактный quality runner | Служебный инструмент запускает проверки, не знает доменную инфраструктуру | Условия SQL/Redis-тестов определены тестами; stdout содержит ошибки и краткий итог |

«Сделать как в проекте» требует сначала найти действующий пример и проверить его
границы. Например, стиль poolx полезен для SQLite API, но копирование его ключа
транзакции без привязки к клиенту воспроизводит ошибку владения контекстом.

## Честные формулировки гарантий

Для существенного исправления нужны четыре пункта: проблема, выбранное решение,
проверка наблюдаемого поведения и оставшееся ограничение. Примеры:

- Mock Redis проверяет реакцию Store на отказ захвата; он не подтверждает TTL
  настоящего Redis. Race detector тоже не доказывает корректность распределённой блокировки.
- SQLite commit/rollback на временном файле проверяет атомарность SQL; не доказывает
  поведение при отключении питания или сохранность диска.
- Outbox исключает потерю события между состоянием и записью события в одной БД;
  повтор после неоднозначного Kafka ACK всё равно возможен.
- Отмена ожидания Docker API не доказывает остановку контейнера. Для остановки
  нужен отдельный ограниченный cleanup context и подтверждение результата.

Если замечание не требует изменения, объяснение должно ссылаться на потребность
сценария. Так приватный этап удаления возвращает Task ради путей очистки **после**
commit; это не возвращаемое HTTP-представление удалённой сущности.

## Как работать с агентом без разрастания контекста

Для локального бага достаточно цели, воспроизведения и ограничений. Для изменения
гарантий доставки полезен короткий план с точкой review перед переключением runtime.
Документация здесь нужна для восстановления контекста; Backlog — для исполнения
конкретной задачи; AGENTS — для постоянных правил.

Размер следующего PR лучше выбирать по одной проверяемой гарантии, например
«не отправлять второй Docker Start после потери ответа», а не «повысить надёжность
всей системы». В отчёте агента должны быть тесты этой гарантии и её пределы.
Для независимой проверки можно попросить отдельное review diff с акцентом на окна
сбоя, а не повторять исходное объяснение реализации.

Пока отдельный skill не нужен: порядок review уже описан в AGENTS, механические
проверки выполняет Go runner. Skill станет полезен, если один и тот же многошаговый
аудит потребуется в нескольких репозиториях; дублировать эти документы ради него
сейчас означало бы создать ещё один расходящийся источник правил.
