# Правила работы над PINN Automizer

## Архитектура и стиль

- Сохранять существующий стиль Go-кода, названия пакетов и структуру проекта. Не проводить массовый рефакторинг или переименование вместе с исправлением поведения.
- DI-интерфейсы именовать по конкретной зависимости: `Postgres`, `SQLite`, `Kafka`, `Redis`, а не `Repository`, `Broker` или `Writer`. Поля и параметры называть соответственно (`sqlite`, `kafka`). Интерфейсы остаются узкими и определяются рядом с потребителем; конкретное имя не разрешает переносить SQL или инфраструктурные типы в бизнес-логику. Не проектировать смену адаптера без реальной потребности.
- Конкретные Kafka-обёртки в `pkg/kafka` и `pkg/kafka/segmentio` именовать `Consumer` и `Producer`, их конфиги — `ConsumerConfig` и `ProducerConfig`. Библиотечные имена `kafka-go.Reader`/`Writer` сохраняются внутри адаптера. DI-интерфейс usecase-а остаётся `Kafka`.
- DI-интерфейс объявлять в файле потребителя непосредственно над структурой usecase-а. Не сжимать объявления структур и функций в одну строку; между самостоятельными объявлениями оставлять пустую строку.
- Пустые `struct{}` и объявления zero value оставлять компактными; правило переносов относится к содержательным объявлениям. Готовую domain/core сущность не перевалидировать в каждом слое: методы принимают валидные значения. `WithIdKey` не может штатно ошибиться. Проверки при создании/восстановлении и проверки допустимости перехода остаются у сущности.
- Нарушение внутреннего persistence-контракта при `row.toDomain()` и недопустимые подтверждённые позиции `kafka.PartialErr` — fail-fast с panic и регрессионным тестом, а не штатная ошибка для повторной обработки. SQL I/O, занятость БД и неизвестный исход Kafka остаются обычными ошибками. Не обещать, что DB CHECK исключает любые неконсистентные записи.
- Каждый usecase описывает конкретное бизнес-требование. Сохранять отдельные пакеты сценариев и узкие интерфейсы зависимостей рядом с потребителем. Если у метода usecase есть хотя бы один бизнес-параметр, передавать их структурой Input, даже при одном поле; бизнес-результаты аналогично возвращать структурой Output. context.Context и error остаются отдельными параметром и результатом; инфраструктурные DI-методы под это правило не подгонять.
- Domain/core сущности создаются только проверяющими конструкторами `New*`, возвращающими ошибку и вызывающими `Validate`. После успешного создания сущность всегда валидна; переходы состояния выполняются только её методами и не оставляют частично изменённое состояние при ошибке. Восстановление из БД проходит через проверяющий конструктор восстановления. DTO/Input/SQL row — непроверенные данные, их нельзя считать сущностями. Не менять поля сущности напрямую и не создавать рабочие сущности литералами, в том числе в фикстурах; отрицательные тесты явно используют входные данные/снимки. Экспортируемые поля legacy-моделей пока позволяют нарушить это правило технически; не выдавать конвенцию за compile-time гарантию и не проводить массовую инкапсуляцию вне задачи.
- Сигнатура должна объяснять результат на текущем уровне абстракции: использовать осмысленные типы, например `limit.Limit`, `core.Created`, `core.Changed`. Корректный повтор уже выполненной операции — нормальный результат, а не ошибка. Не заставлять читателя смотреть реализацию ради смысла чисел и bool.
- Читать API должно быть удобно от вызывающего кода к зависимостям: именовать параметры, возвращаемые результаты и константы по смыслу на текущем уровне абстракции. Общие результаты (`core.Created`, `core.Changed`) размещать в `core` и сохранять их тип в Output; протокольные контракты ошибок — в пакете соответствующего адаптера (`kafka.PartialErr`). Не объявлять один и тот же контракт заново у каждого потребителя. Ошибку возвращать только при возможном штатном отказе, а не ради повторной проверки валидных аргументов, включая `limit.Limit`.
- Длинные сигнатуры функций и методов, включая DI-интерфейсы, разбивать на несколько строк: по одному аргументу на строку, закрывающая скобка на отдельной строке. Сгенерированные моки вручную не форматировать.
- Содержательные struct literals, конструкторы, SQL builder chains и SetMap разбивать на строки по полям/этапам. Между самостоятельными функциями оставлять пустую строку; не превращать правило переносов в механическое растягивание пустых типов и простых выражений.
- В SQL-адаптере `repository.go` содержит интерфейсы, структуру и New/Close; запросы разделять по сущностям/сценариям в `*_repository.go`. В `schema.go` сначала полностью описывать одну таблицу (table/column constants, список колонок, row и Values), затем следующую. Вспомогательные вложенные row размещать после полного блока таблицы, не между её константами и основной row. У вложенной row есть свой Values, составная row использует его. Конструкторы row (`newAttemptRow` и подобные) и преобразования domain/row размещать в `converters.go` или тематических `*_converters.go`; они не принадлежат методам запросов.
- Для проверки принадлежности использовать set `map[T]struct{}`, если отдельное значение не требуется; не кодировать множество через `map[T]bool`.
- Простые проверки входных полей поручать существующему `validate.V`, вручную описывать связи полей и бизнес-переходы. Не пересоздавать сущность конструктором ради её повторной проверки. Подготовка raw row из валидной сущности не требует новой domain-валидации.
- Использовать стандартные `slices.Clone` и `maps.Clone` для копирования. Передавать UUID в query builder как значение, если драйвер поддерживает его `Valuer`; String нужен для текстового представления на wire. Общие SQL/time-механизмы держать в shared-клиенте, не копировать в сервисы и не обобщать на все RDBMS без потребителя.
- Docker SDK и его типы/ошибки локализовать в shared `pkg/docker`. Потребители описывают узкий интерфейс `Docker` на собственных DTO shared-адаптера; бизнес-слой solver не импортирует Moby/containerd. Протокольные тесты SDK принадлежат shared-адаптеру; unit-тесты PinnRunner используют сгенерированные моки.
- HTTP handlers и Kafka consumers отвечают за транспорт и преобразование сообщений. Бизнес-правила остаются в usecase-ах и domain; SQL, Redis, файловые операции и Docker API — в адаптерах.
- После захвата ресурса сразу предусматривать `defer` освобождения: временные ресурсы закрываются в текущем методе, долговременные передаются владельцу и закрываются его `Close`. Неуспешный конструктор освобождает всё уже захваченное; транзакция получает `defer Rollback`. Конструкторы разделять на осмысленные приватные этапы, чтобы порядок и передача владения читались явно. Ошибки закрытия не терять, когда они влияют на результат операции.
- Общие инфраструктурные механизмы в монорепозитории размещать в shared `pkg`; адаптеры конкретного сервиса описывают его domain-операции поверх общего клиента. SQLite connection/ownership — `pkg/sqlite`, SQL попыток solver — его внутренний адаптер.
- Для SQL-миграций использовать внешний goose через Docker Compose и make, как для auth/tasks. Новое изменение — отдельный SQL-файл только с `Up`; Down не добавлять и не запускать. Не встраивать миграции в бинарь и не применять их при открытии адаптера. SQL-файлы доставляются отдельно; runtime проверяет готовность схемы. Применённые файлы не редактировать, исправление оформлять следующей Up. Неуспешная Up откатывается транзакцией. SQLite migration command и runtime используют один ownership lock.
- Не объединять сценарии в универсальный сервис и не вводить инфраструктурные абстракции без конкретной необходимости.
- API уравнения будет изменено отдельно. Не менять текущий контракт PINN, набор входных файлов или формат результатов без необходимости для согласованного исправления. Специфику Python и Docker локализовать в адаптерах.

## Отказоустойчивость

- Для каждой операции рассматривать повтор запроса, повторную доставку события, конкурентное выполнение, отмену контекста и остановку процесса между внешними эффектами.
- Не обещать exactly-once между PostgreSQL, Kafka, Redis и файловой системой. Использовать устойчивые записи операций, transactional outbox и идемпотентных потребителей там, где этого требует сценарий.
- Изменение состояния задачи и создание соответствующего outbox-события должны быть одной транзакцией PostgreSQL.
- Не переключать solver на at-least-once без защиты от повторного вычисления и восстановления попытки выполнения.
- Идемпотентность должна учитывать пользователя, операцию и параметры запроса. Повтор ключа с другими параметрами должен давать конфликт. Redis TTL не должен быть единственным источником истины о выполненной операции.
- Защищать переходы состояния условными изменениями в БД или блокировками. Одна транзакция вокруг SELECT и UPDATE сама по себе не устраняет гонку.
- Учитывать, что события из разных Kafka-топиков могут обрабатываться в обратном порядке. Повтор применённого события не должен портить результат или бесконечно повторяться.
- Не держать транзакции БД открытыми во время длительного файлового I/O или вычислений. Для внешних эффектов предусматривать компенсацию или устойчивую повторяемую очистку.
- Timeout ожидания Docker API не означает остановку контейнера. Предусматривать явную остановку и очистку с отдельным ограниченным контекстом.
- При shutdown сначала остановить приём работы, завершить или корректно прервать workers, дождаться их и затем закрыть зависимости. Контекст очистки не наследует уже отменённый контекст.
- Ошибка критического consumer-а не должна оставлять сервис внешне работоспособным без обработки очереди.
- Сроки жизни кешей авторизации должны соответствовать сроку сессии и явно выбранным гарантиям отзыва.

## Работа в репозитории

- Один PR — одно связное изменение; целевой размер до 1000 изменённых строк, предел 2000 (добавления + удаления относительно PR base, включая тесты и generated mocks). Перед публикацией проверять `git diff --shortstat <base>...HEAD`. При приближении к пределу выделять следующий самостоятельный PR; не сокращать тесты ради лимита. Превышение заранее согласовать с пользователем.
- Backlog вести для крупных самостоятельных результатов, рисков и отложенных решений. Мелкие исправления и раунды review учитывать в существующем PR, без отдельной задачи на каждый раунд. Карточка: цель, 2–5 критериев, при необходимости краткий план; итог — ссылка на PR, проверки и оставшиеся ограничения. Не копировать переписку, список коммитов и пошаговый журнал.
- Экономить контекст: результат инструментов фильтровать до вывода модели. Для review до вывода модели отбирать только новые или отредактированные сообщения пользователя в незарезолвленных обсуждениях (путь, ID, текст). Зарезолвленные обсуждения и уже обработанные сообщения повторно не читать; прежний контекст открывать адресно только при необходимости понять новый ответ. Не выводить полную историю и метаданные GitHub. Читать нужные разделы документов; не дублировать одно решение в backlog, docs и ответе. Overview Backlog читать один раз за разговор, подробные guides — только при соответствующем действии и если ещё не прочитаны.


- Накопительная ветка проекта — `codex/task-progress`, созданная от `dev`. Каждую задачу выполнять в отдельной ветке `codex/<task-name>` от актуальной накопительной ветки. PR направлять в `codex/task-progress`; исправления review добавлять в тот же PR. Вливать после review пользователя и необходимых проверок, затем начинать следующую задачу от обновлённой базы. Не писать напрямую в `dev`, `main`/`master` или накопительную ветку. Ранее выполненная работа остаётся в `codex/fault-tolerance` до переноса через review.
- Перед изменениями проверять git status. Сохранять пользовательские изменения и staged deletion; не выполнять reset, restore или stash без явного запроса.
- Ответы, публикуемые агентом в GitHub, начинать с `[Codex]`, чтобы отличать их от сообщений пользователя при общем GitHub-доступе. Не менять Git author или аккаунт GitHub без отдельного запроса.
- Review обрабатывать небольшими партиями: прочитать только новые апдейты незарезолвленных обсуждений и актуальный diff затронутых файлов, затем только затронутый код. Для каждого замечания записывать кратко «исправлено / требуется уточнение / не применимо» с причиной и проверкой; не перечитывать весь репозиторий без новой причины. Правки коммитить связанными группами; не закрывать обсуждение вместо решения ревьюера.
- Завершённые и проверенные задачи оформлять коммитами вместе с новыми тестами и записями backlog. Перед коммитом проверять состав staged diff; не включать несвязанные пользовательские изменения.
- Не читать и не выводить содержимое .env и другие секреты ради диагностики. Использовать .env.example и конфигурационный код.
- Не запускать очистку окружения, удаление volume-ов, миграции действующей БД, deploy или длительные PINN-вычисления без соответствующего запроса.
- Реальные дефекты исправлять небольшими связанными изменениями. Не добавлять зависимости, новые сервисы или новое хранилище только ради предполагаемого будущего масштаба.

## Проверки и объяснения

- Обучать пользователя по ходу работы, привязывая объяснения к конкретным изменениям. Для существенного решения кратко раскрывать проблему, выбранный подход, альтернативы и компромиссы; показывать, как такой сценарий обычно решают в production и почему. Отличать подходящий для текущего масштаба вариант от мер, необходимых при росте нагрузки или требований.
- Замечать места, где стоит изменить, добавить или убрать код, проверки либо инфраструктуру. Объяснять ожидаемую пользу и цену усложнения. Предложения за пределами текущей задачи отделять от реализации; не расширять её незаметно.
- Обучать работе с AI-агентом: по ситуации объяснять, как задавать цель и ограничения, выбирать размер задачи, передавать контекст, проверять результат и использовать независимую проверку. Показывать, когда достаточно прямой команды, когда полезен план, а когда требуется явное согласование решения. Не превращать каждый шаг в лекцию.
- Если повторяющаяся процедура оправдывает отдельный skill, предложить его пользователю и аргументировать: какие повторения он устранит, когда должен включаться и почему AGENTS.md или обычного скрипта недостаточно. Не создавать skill только из-за наличия похожих ключевых слов.
- Сохранять краткость обучения: обычно одно полезное объяснение на существенное решение; подробности добавлять по запросу или когда они нужны для оценки риска. Не пересказывать документацию и вывод инструментов целиком.
- Единый формат Go: `gofmt`, затем `gci`; импорты разделять на стандартную библиотеку, сторонние пакеты и `github.com/AridanWarlock/pinnAutomizer`. Не сортировать их вручную: после изменений запускать `make fmt`.
- Перед коммитом запускать `make check`: форматирование, закреплённый golangci-lint, самопроверки runner-а и тесты пяти модулей. Установка инструмента — `make tools-install`; версия и конфигурация хранятся в репозитории.
- Использовать проверки корректности `govet`, `ineffassign`, `staticcheck SA*`, `unused`. Не включать все линтеры и стилевые советы ради количества правил. Миграции deprecated API проверять отдельно; не скрывать реальные ошибки широкими `nolint`.
- Тесты запускать через `make test`; адресно — `make test TEST_ARGS='-run TestName ./path/to/package'`, с race detector — `make test-race`. При передаче TEST_ARGS указывать пакеты вместе с флагами.
- Runner качества реализован на Go в `pkg/cmd/quality`; `make` собирает игнорируемый `.tools/quality` с `GOWORK=off`. Python разрешён как инструмент агента для анализа и редактирования. Ограничение касается добавления служебных Python-скриптов и зависимости от Python в исходники, сборку и CI проекта; существующий Python-контракт PINN сохраняется. Полный `make check` включает Go-тесты runner-а; не запускать их второй раз без причины.
- Читать только краткий итог или диагностику упавших тестов/сборки. Runner возвращает настоящий ненулевой код при ошибке, выводит максимум 20 строк и сохраняет полный лог в `out/quality/`. Не запускать `go test -v` и не читать весь лог без конкретной причины; для уточнения повторять только упавший тест или нужный участок лога.
- Успех тестов без `PINN_TEST_POSTGRES_DSN` не доказывает SQL-гарантии: интеграционные тесты PostgreSQL в таком запуске пропускаются через `t.Skip`; сообщения находятся в полном тестовом логе. Runner не знает о конкретных БД и именах env-переменных. CI включает одноразовую тестовую БД.
- `AGENTS.md` содержит постоянные правила этого проекта; skill нужен для повторяемой процедуры, которую стоит загружать только для соответствующей задачи. Не дублировать правила и команды в skill без пользы.
- Карта текущей архитектуры, причины требований review и дальнейшие шаги находятся в `docs/README.md`. Читать только нужный документ; перед изменением runtime сверять подключение в `cmd/main.go`, чтобы не считать подготовленный адаптер уже работающей гарантией.
- Объяснять пользователю существенные решения по-русски: какой сценарий сбоя возможен, как изменение его устраняет и какие ограничения остаются. Отделять подтверждённые дефекты от предположений.
- Сначала восстановить компиляцию существующих тестов. Обновлять моки по актуальным интерфейсам; не удалять действующие проверки ради зелёной сборки.
- Mockery настраивать общими параметрами и рекурсивно по всем Go-модулям монорепозитория. Не перечислять отдельные DI-интерфейсы в `.mockery.yml`, если нет согласованного исключения.
- При изменении интерфейса в той же задаче перегенерировать связанные моки, обновить затронутые тесты и запустить их. Сгенерированные моки хранить в Git и коммитить вместе с интерфейсом и тестами; после pull не рассчитывать на автоматическую генерацию. Использовать закреплённую версию генератора, не редактировать мок-файлы вручную и проверять diff, чтобы генерация не затронула несвязанные пакеты.
- Для исправлений отказоустойчивости добавлять проверки наблюдаемого поведения: повтор, конкуренция, частичный сбой, отмена. Не писать тесты, которые только повторяют реализацию.
- Unit-тесты делать короткими, независимыми и быстрыми: понятные имена сценариев, небольшие фикстуры, без sleep и внешнего I/O. Независимые случаи можно запускать через t.Parallel; синхронизацию проверять каналами, а не задержками. SQL/crash-гарантии по-прежнему проверять отдельными интеграционными тестами.
- Для конкурентного кода использовать race detector, когда это доступно. Для гарантий SQL и внешних систем нужны интеграционные проверки; моки не доказывают атомарность.
- Базовая команда: go test ./pkg/... ./services/auth/... ./services/tasks/... ./services/solver/... ./services/gateway/.... Если sandbox запрещает штатный build cache, задать GOCACHE в доступном временном каталоге.
- Сообщать, какие проверки выполнены, какие не прошли и какие интеграционные сценарии не проверялись. Не выдавать статический анализ за подтверждённое поведение работающей системы.
