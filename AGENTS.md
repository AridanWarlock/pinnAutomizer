# Правила работы над PINN Automizer

## Архитектура и стиль

- Сохранять существующий стиль Go-кода, названия пакетов и структуру проекта. Не проводить массовый рефакторинг или переименование вместе с исправлением поведения.
- DI-интерфейсы именовать по конкретной зависимости: `Postgres`, `SQLite`, `Kafka`, `Redis`, а не `Repository`, `Broker` или `Writer`. Поля и параметры называть соответственно (`sqlite`, `kafka`). Интерфейсы остаются узкими и определяются рядом с потребителем; конкретное имя не разрешает переносить SQL или инфраструктурные типы в бизнес-логику. Не проектировать смену адаптера без реальной потребности.
- Конкретные Kafka-обёртки в `pkg/kafka` и `pkg/kafka/segmentio` именовать `Consumer` и `Producer`, их конфиги — `ConsumerConfig` и `ProducerConfig`. Библиотечные имена `kafka-go.Reader`/`Writer` сохраняются внутри адаптера. DI-интерфейс usecase-а остаётся `Kafka`.
- Каждый usecase описывает конкретное бизнес-требование. Сохранять отдельные пакеты сценариев, Input/Output и узкие интерфейсы зависимостей рядом с потребителем.
- HTTP handlers и Kafka consumers отвечают за транспорт и преобразование сообщений. Бизнес-правила остаются в usecase-ах и domain; SQL, Redis, файловые операции и Docker API — в адаптерах.
- После захвата ресурса сразу предусматривать `defer` освобождения: временные ресурсы закрываются в текущем методе, долговременные передаются владельцу и закрываются его `Close`. Неуспешный конструктор освобождает всё уже захваченное; транзакция получает `defer Rollback`. Конструкторы разделять на осмысленные приватные этапы, чтобы порядок и передача владения читались явно. Ошибки закрытия не терять, когда они влияют на результат операции.
- Для SQL-миграций использовать goose, как в существующем проекте. Новое изменение схемы — отдельный SQL-файл; применённые миграции не редактировать. Не вводить ручные `schemaVersion`/`PRAGMA user_version` рядом с goose. SQLite-миграции встроены в бинарь и применяются под ownership lock; автоматический Down запрещён. Старую схему без истории миграций не принимать за актуальную без проверенной процедуры перехода.
- Не объединять сценарии в универсальный сервис и не вводить инфраструктурные абстракции без конкретной необходимости.
- API уравнения будет изменено отдельно. Не менять текущий контракт PINN, набор входных файлов или формат результатов без необходимости для согласованного исправления. Специфику Python и Docker локализовать в адаптерах.

## Отказоустойчивость

- Для каждой операции рассматривать повтор запроса, повторную доставку события, конкурентное выполнение, отмену контекста и остановку процесса между внешними эффектами.
- Не обещать exactly-once между PostgreSQL, Kafka, Redis и файловой системой. Использовать устойчивые записи операций, transactional outbox и идемпотентных потребителей там, где этого требует сценарий.
- Изменение состояния задачи и создание соответствующего outbox-события должны быть одной транзакцией PostgreSQL.
- Не переключать solver на at-least-once без защиты от повторного вычисления и восстановления попытки выполнения.
- Идемпотентность должна учитывать пользователя, операцию и параметры запроса. Повтор ключа с другими параметрами должен давать конфликт. Redis TTL не должен быть единственным источником истины о выполненной операции.
- Защищать переходы состояния условными изменениями в БД или блокировками. Одна транзакция вокруг SELECT и UPDATE сама по себе не устраняет гонку.
- Учитывать, что события из разных Kafka-топиков могут обрабатываться в обратном порядке. Повтор применённого события не должен портить результат или бесконечно повторяться.
- Не держать транзакции БД открытыми во время длительного файлового I/O или вычислений. Для внешних эффектов предусматривать компенсацию или устойчивую повторяемую очистку.
- Timeout ожидания Docker API не означает остановку контейнера. Предусматривать явную остановку и очистку с отдельным ограниченным контекстом.
- При shutdown сначала остановить приём работы, завершить или корректно прервать workers, дождаться их и затем закрыть зависимости. Контекст очистки не наследует уже отменённый контекст.
- Ошибка критического consumer-а не должна оставлять сервис внешне работоспособным без обработки очереди.
- Сроки жизни кешей авторизации должны соответствовать сроку сессии и явно выбранным гарантиям отзыва.

## Работа в репозитории

- Работать в ветке с префиксом codex/. Для текущего направления создана codex/fault-tolerance. Не писать в dev/main напрямую.
- Перед изменениями проверять git status. Сохранять пользовательские изменения и staged deletion; не выполнять reset, restore или stash без явного запроса.
- Завершённые и проверенные задачи оформлять коммитами вместе с новыми тестами и записями backlog. Перед коммитом проверять состав staged diff; не включать несвязанные пользовательские изменения.
- Не читать и не выводить содержимое .env и другие секреты ради диагностики. Использовать .env.example и конфигурационный код.
- Не запускать очистку окружения, удаление volume-ов, миграции действующей БД, deploy или длительные PINN-вычисления без соответствующего запроса.
- Реальные дефекты исправлять небольшими связанными изменениями. Не добавлять зависимости, новые сервисы или новое хранилище только ради предполагаемого будущего масштаба.

## Проверки и объяснения

- Обучать пользователя по ходу работы, привязывая объяснения к конкретным изменениям. Для существенного решения кратко раскрывать проблему, выбранный подход, альтернативы и компромиссы; показывать, как такой сценарий обычно решают в production и почему. Отличать подходящий для текущего масштаба вариант от мер, необходимых при росте нагрузки или требований.
- Замечать места, где стоит изменить, добавить или убрать код, проверки либо инфраструктуру. Объяснять ожидаемую пользу и цену усложнения. Предложения за пределами текущей задачи отделять от реализации; не расширять её незаметно.
- Обучать работе с AI-агентом: по ситуации объяснять, как задавать цель и ограничения, выбирать размер задачи, передавать контекст, проверять результат и использовать независимую проверку. Показывать, когда достаточно прямой команды, когда полезен план, а когда требуется явное согласование решения. Не превращать каждый шаг в лекцию.
- Если повторяющаяся процедура оправдывает отдельный skill, предложить его пользователю и аргументировать: какие повторения он устранит, когда должен включаться и почему AGENTS.md или обычного скрипта недостаточно. Не создавать skill только из-за наличия похожих ключевых слов.
- Сохранять краткость обучения: обычно одно полезное объяснение на существенное решение; подробности добавлять по запросу или когда они нужны для оценки риска. Не пересказывать документацию и вывод инструментов целиком.
- Единый формат Go: `gofmt`, затем `gci`; импорты разделять на стандартную библиотеку, сторонние пакеты и `github.com/AridanWarlock/pinnAutomizer`. Не сортировать их вручную: после изменений запускать `make fmt`.
- Перед коммитом запускать `make check`: форматирование, закреплённый golangci-lint, самопроверки runner-а и тесты пяти модулей. Установка инструмента — `make tools-install`; версия и конфигурация хранятся в репозитории.
- Использовать проверки корректности `govet`, `ineffassign`, `staticcheck SA*`, `unused`. Не включать все линтеры и стилевые советы ради количества правил. Миграции deprecated API проверять отдельно; не скрывать реальные ошибки широкими `nolint`.
- Тесты запускать через `make test`; адресно — `make test TEST_ARGS='-run TestName ./path/to/package'`, с race detector — `make test-race`. При передаче TEST_ARGS указывать пакеты вместе с флагами.
- Runner качества реализован на Go в `pkg/cmd/quality`; `make` собирает игнорируемый `.tools/quality` с `GOWORK=off`. Для служебных проверок backend не добавлять Python runtime. Полный `make check` включает Go-тесты runner-а; не запускать их второй раз без причины.
- Читать только краткий итог или диагностику упавших тестов/сборки. Runner возвращает настоящий ненулевой код при ошибке, выводит максимум 20 строк и сохраняет полный лог в `out/quality/`. Не запускать `go test -v` и не читать весь лог без конкретной причины; для уточнения повторять только упавший тест или нужный участок лога.
- Успех тестов без `PINN_TEST_POSTGRES_DSN` не доказывает SQL-гарантии: интеграционные тесты PostgreSQL в таком запуске пропускаются, runner явно сообщает об этом. CI включает одноразовую тестовую БД.
- `AGENTS.md` содержит постоянные правила этого проекта; skill нужен для повторяемой процедуры, которую стоит загружать только для соответствующей задачи. Не дублировать правила и команды в skill без пользы.
- Объяснять пользователю существенные решения по-русски: какой сценарий сбоя возможен, как изменение его устраняет и какие ограничения остаются. Отделять подтверждённые дефекты от предположений.
- Сначала восстановить компиляцию существующих тестов. Обновлять моки по актуальным интерфейсам; не удалять действующие проверки ради зелёной сборки.
- При изменении интерфейса в той же задаче перегенерировать связанные моки, обновить затронутые тесты и запустить их. Сгенерированные моки хранить в Git и коммитить вместе с интерфейсом и тестами; после pull не рассчитывать на автоматическую генерацию. Использовать закреплённую версию генератора, не редактировать мок-файлы вручную и проверять diff, чтобы генерация не затронула несвязанные пакеты.
- Для исправлений отказоустойчивости добавлять проверки наблюдаемого поведения: повтор, конкуренция, частичный сбой, отмена. Не писать тесты, которые только повторяют реализацию.
- Для конкурентного кода использовать race detector, когда это доступно. Для гарантий SQL и внешних систем нужны интеграционные проверки; моки не доказывают атомарность.
- Базовая команда: go test ./pkg/... ./services/auth/... ./services/tasks/... ./services/solver/... ./services/gateway/.... Если sandbox запрещает штатный build cache, задать GOCACHE в доступном временном каталоге.
- Сообщать, какие проверки выполнены, какие не прошли и какие интеграционные сценарии не проверялись. Не выдавать статический анализ за подтверждённое поведение работающей системы.

## Исходное состояние

- До начала исправлений присутствовали пользовательские изменения в auth/refresh, PostgreSQL-адаптере refresh tokens и Docker runner, а также staged deletion mocks_test.go для tasks/run.
- Первый общий запуск тестов выявил устаревшие моки в auth/refresh, tasks/create, tasks/get, tasks/afterRun, tasks/outbox и middleware gateway. В том же запуске упал TestBucket_Cleanup. Это наблюдения исходного состояния, а не основание пропускать проверки.
- По явному разрешению пользователя старые изменения сброшены. Мок tasks/run восстановлен и перегенерирован под новые интерфейсы; тесты refresh согласованы с исходным поведением без старой очистки сессий.
