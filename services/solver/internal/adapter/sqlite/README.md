# Журнал solver

Этот адаптер пока не подключён к runtime solver. Текущий consumer и Docker runner сохраняют прежнее поведение; переключение доставки выполняется отдельным этапом TASK-3 после проверки восстановления контейнеров.

`New(Config)` требует путь к локальному файлу и положительный `BusyTimeout`. Каталог должен находиться на постоянном диске/volume. Сохранять следует весь каталог, включая файлы `-wal` и `-shm`; копирование одного работающего `.db` не является корректным backup. Сетевые файловые системы и несколько Docker-host не входят в поддерживаемую схему.

Журнал использует WAL, synchronous=FULL, foreign_keys и bounded busy_timeout. Единственный владелец удерживает системную блокировку `.lock` до закрытия SQL connections. Файл блокировки не удаляется: удаление позволило бы другому процессу открыть новый inode и обойти владельца. При смерти процесса ОС освобождает блокировку. Потеря диска/host потребует отдельного решения восстановления.

`RegisterAttempt` сопоставляет run_id, task_id и mode. Повтор той же команды возвращает сохранённую попытку; изменённые параметры либо новая попытка той же задачи дают конфликт. Это соответствует текущему API с одним запуском задачи. UUID команды должен приходить из `X-Idempotency-Key` события tasks outbox; старые сообщения без такого UUID потребуют решения при переключении consumer.

`RecordContainer` сохраняет идентификатор. `RequestStart` атомарно записывает намерение и deadline перед Docker Start. Только результат `true` разрешает первый Start. Повтор возвращает `false` и сохраняет первоначальный deadline. После неоднозначного Start нужно исследовать контейнер: второй Start может заново запустить уже завершившийся контейнер. Сохранённое намерение само по себе не доказывает запуск Docker.

`FinishAttempt` сохраняет результат и outbox-событие одной короткой транзакцией. Повтор завершения не заменяет первый результат. ID события передаётся в его заголовке `X-Idempotency-Key`; поля partition, offset и time не принимаются, поскольку журнал хранит исходящее сообщение, а не метаданные доставки.

Usecase outbox публикует по одному сообщению и удаляет запись только после подтверждения синхронного writer. Потерянное подтверждение приводит к повтору с теми же key/value/headers. Поэтому получатель должен быть идемпотентным. `Run` выполняется в goroutine, принадлежащей supervisor: сначала отменить контекст, затем дождаться возврата, затем закрыть writer и журнал. Writer должен соблюдать контекст. Ошибки передаются callback-у и повторяются с заданным интервалом.

Проверки используют реальный SQLite на временном диске: конкуренция, откат транзакции, busy lock, reopen и SIGKILL владельца. Они не доказывают сохранность при отключении питания, доставку настоящим Kafka broker или поведение Docker.
