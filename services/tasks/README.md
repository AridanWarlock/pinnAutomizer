# Состояния задач и повтор запуска

Usecase-ы `run`, `delete`, `onRun` и `afterRun` читают изменяемую задачу через
`FOR UPDATE` внутри PostgreSQL-транзакции. Конкурирующие изменения одной задачи
ждут друг друга; после ожидания решение принимается по актуальному состоянию.

`onRun` переводит `in_queue` в `running`. Повтор для `running` или завершённой
задачи ничего не меняет. `afterRun` принимает результат из `in_queue` или
`running`: события начала и конца из разных Kafka-топиков могут обработаться
в обратном порядке. Первый сохранённый итог окончательный. Повторные попытки
вычисления пока не поддерживаются; для них потребуется отдельный `run_id`.

Удаление запрещено для `in_queue` и `running`. Файлы удаляются только после
commit удаления записи. Ошибки очистки логируются; восстановление очистки
после остановки процесса пока не реализовано.

## Идемпотентность HTTP

Клиент передаёт стабильный `X-Idempotency-Key` длиной от 1 до 256 байт в
`POST /api/v1/tasks/{id}/run` и использует его при повторе того же запроса.
Если ключ не передан, middleware создаёт новый ключ; для повторов после
потерянного ответа клиент должен задавать его самостоятельно.

Ключ относится к операции запуска и пользователю. Повтор ключа для той же
задачи возвращает 204, для другой задачи того же пользователя — 409.
Другой пользователь может использовать такой же текст ключа для своей задачи.
Конкурирующие запросы с одним ключом ждут исхода первой транзакции.

Принятый запрос, статус `in_queue` и outbox-событие сохраняются одной транзакцией.
Если она откатилась, запрос можно повторить. Если commit состоялся, но ответ
потерялся, повтор читает сохранённый запрос и не создаёт новое событие.
Идентификатор события — отдельный UUID, а не клиентский ключ.

Redis для сервиса tasks больше не требуется. Auth и gateway продолжают
использовать Redis. Эти гарантии относятся к принятию запуска; восстановление
самого вычисления после падения solver-а остаётся отдельной задачей.

## Обновление схемы

Перед запуском обновлённого tasks требуется миграция
`20261013190000_create_task_run_requests.sql` стандартным процессом проекта
(`make tasks-goose-up`). Изменение исходников не применяет миграцию автоматически.
Запросы, принятые старой версией до появления таблицы, не имеют сохранённого
результата в ней: новые гарантии повторов действуют для запросов новой версии.

Записи `task_run_requests` сохраняются после отправки outbox и удаления задачи,
чтобы поздний повтор оставался идемпотентным. Автоматического удаления этих
записей пока нет: срок хранения и допустимое окно повторов требуют отдельной
политики. Ручное удаление записей сокращает гарантии идемпотентности.

## Интеграционные проверки

Задать `PINN_TEST_POSTGRES_DSN` для отдельного одноразового PostgreSQL-кластера
с правом CREATE DATABASE и выполнять из корня репозитория:

```sh
go test -race ./services/tasks/internal/adapter/postgres ./services/tasks/internal/domain ./services/tasks/internal/usecases/v1/tasks/delete ./pkg/redis/indempotency
```

Без переменной тесты БД явно пропускаются. Каждый тест создаёт собственную БД
`pinn_test_*`, применяет новую миграцию к ней и удаляет эту БД после проверки.
Использовать отдельный тестовый кластер: тесты не предназначены для рабочей БД.
Проверяются оба порядка `run/delete`, повторные и переставленные события,
конкурирующие завершения, область ключа, повтор после удаления outbox и задачи,
откат при ошибке сохранения события и потерянное подтверждение commit.
