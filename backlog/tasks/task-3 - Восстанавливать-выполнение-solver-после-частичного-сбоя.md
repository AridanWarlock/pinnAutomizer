## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
At-most-once чтение и отсутствие устойчивой попытки запуска могут оставить задачу в очереди или running после остановки процесса либо ошибки публикации результата.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 Повтор сообщения не запускает второе вычисление одной попытки
- [ ] #2 Завершение попытки восстанавливается после сбоя публикации результата
- [ ] #3 Интеграционные проверки покрывают остановку между запуском и завершением
<!-- AC:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
План для архитектурного согласования, до реализации. 1. Ledger попыток выполнения принадлежит solver: отдельная PostgreSQL-БД/учётная запись, которую можно физически разместить на существующем сервере PostgreSQL; чужие таблицы tasks/auth solver не изменяет. 2. Стабильный run_id взять из UUID outbox-события запуска; сохранять task_id, mode, статус, container_id/детерминированное имя, deadline и итог. Повтор того же run_id с другим содержимым — конфликт. Новые попытки/retry API уравнения сейчас не добавлять. 3. Сохранить этапы регистрации/создания/запроса старта/выполнения/окончательного результата. До Docker Start атомарно фиксировать start_requested: повторный обработчик не отправляет новый Start для этой попытки. Результат и события solver outbox сохранять одной транзакцией; не держать DB-транзакцию во время вычисления. 4. Контейнер получает стабильное имя и labels; AutoRemove отключить, чтобы после падения solver Docker сохранил exit code. При восстановлении running — наблюдать существующий контейнер, exited — сохранять результат. При неоднозначном исходе Start или утрате контейнера после start_requested не запускать вычисление заново: фиксировать диагностируемый error/неопределённый исход и останавливать/очищать контейнер. Lease/heartbeat помогают обнаружить недоступного worker, но не являются сами по себе fencing Docker-команд. 5. Разделить usecase запуска, usecase восстановления незавершённых попыток и инфраструктурный outbox worker; HTTP/Kafka consumer остаётся транспортом. Восстановление выполнять при запуске и периодически, с условными обновлениями/координацией владельца и без долгих DB-транзакций. 6. Очищать контейнер только после устойчивого сохранения итога и события; явный Stop/Kill и ограниченный отдельный cleanup-контекст при deadline. При graceful shutdown прекращать приём и наблюдение, сохраняя восстанавливаемую попытку; при временной недоступности Docker/БД не считать контейнер отсутствующим и не публиковать ложный окончательный результат. 7. Только после защиты повторов переключить solver на at-least-once; предусмотреть rollout старых сообщений/контейнеров и совместимость событий с tasks. 8. Проверить duplicate/concurrent handlers, потерю ответа Docker create/start, остановку процесса до/после старта и завершения, недоступность БД/Kafka/Docker, повтор публикации, timeout и очистку. Использовать отдельные PostgreSQL/Kafka и короткий тестовый CPU-контейнер, без PINN/GPU. Ограничение: восстановление гарантируется при сохранности ledger и доступности исходного Docker-host; потеря хоста не превращается в доказанное успешное вычисление.
