## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
At-most-once чтение и отсутствие устойчивой попытки запуска могут оставить задачу в очереди или running после остановки процесса либо ошибки публикации результата.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 Повтор сообщения не запускает второе вычисление одной попытки
- [ ] #2 Завершение попытки восстанавливается после сбоя публикации результата
- [ ] #3 Интеграционные проверки покрывают остановку между запуском и завершением
<!-- AC:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
Пересмотренный план: SQLite для текущего одного Docker-host; реализация ещё не начата. 1. Ledger попыток выполнения принадлежит solver: локальная SQLite на постоянном volume в отдельном каталоге; монтировать каталог вместе с WAL-файлами. Использовать WAL, synchronous=FULL, bounded busy_timeout и короткие транзакции. Чужие таблицы tasks/auth solver не изменяет. Один активный процесс solver владеет данным локальным журналом; параллельный старт с тем же журналом должен безопасно отклоняться, а владение освобождаться при смерти процесса. 2. Стабильный run_id взять из UUID outbox-события запуска; сохранять task_id, mode, статус, container_id/детерминированное имя, deadline и итог. Повтор того же run_id с другим содержимым — конфликт. Новые попытки/retry API уравнения сейчас не добавлять. 3. Сохранить этапы регистрации/создания/запроса старта/выполнения/окончательного результата. До Docker Start атомарно фиксировать start_requested: повторный обработчик не отправляет новый Start для этой попытки. Результат и события solver outbox сохранять одной транзакцией; не держать DB-транзакцию во время вычисления. 4. Контейнер получает стабильное имя и labels; AutoRemove отключить, чтобы после падения solver Docker сохранил exit code. При восстановлении running — наблюдать существующий контейнер, exited — сохранять результат. При неоднозначном исходе Start или утрате контейнера после start_requested не запускать вычисление заново: фиксировать диагностируемый error/неопределённый исход и останавливать/очищать контейнер. Lease/heartbeat помогают обнаружить недоступного worker, но не являются сами по себе fencing Docker-команд. 5. Разделить usecase запуска, usecase восстановления незавершённых попыток и инфраструктурный outbox worker; HTTP/Kafka consumer остаётся транспортом. Восстановление выполнять при запуске и периодически, с условными обновлениями/координацией владельца и без долгих DB-транзакций. 6. Очищать контейнер только после устойчивого сохранения итога и события; явный Stop/Kill и ограниченный отдельный cleanup-контекст при deadline. При graceful shutdown прекращать приём и наблюдение, сохраняя восстанавливаемую попытку; при временной недоступности Docker/БД не считать контейнер отсутствующим и не публиковать ложный окончательный результат. 7. Только после защиты повторов переключить solver на at-least-once; предусмотреть rollout старых сообщений/контейнеров и совместимость событий с tasks. 8. Проверить duplicate/concurrent handlers, потерю ответа Docker create/start, остановку процесса до/после старта и завершения, недоступность БД/Kafka/Docker, повтор публикации, timeout и очистку. Использовать временную SQLite-БД на диске, отдельную Kafka и короткий тестовый CPU-контейнер, без PINN/GPU; проверить восстановление после принудительной остановки, SQLITE_BUSY, сохранность WAL и повторное открытие файла. Для backup использовать согласованный механизм SQLite, не копирование одного активного db-файла. Ограничение: восстановление гарантируется при сохранности ledger и доступности исходного Docker-host; потеря хоста не превращается в доказанное успешное вычисление. Для общего журнала нескольких Docker-host или failover вычисления на другой хост пересмотреть хранение в пользу общего серверного хранилища; текущая локальная SQLite этого не обеспечивает.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
План подготовлен для совместного разбора. Требуется подтвердить новое архитектурное решение: собственное устойчивое хранилище solver и консервативная обработка неоднозначного старта. Код TASK-3 пока не менялся; автоматический повтор вычисления и новый пользовательский API попыток не входят в текущую задачу.

После разбора с пользователем PostgreSQL для solver заменён в плане на локальную SQLite: текущий объём метаданных и один Docker-host не требуют отдельной серверной БД. Сохраняются атомарные ledger/outbox, стабильный run_id и запрет слепого повторного Start. Ограничения: постоянный локальный volume, WAL, один владелец журнала; потерю хоста/диска и общий журнал нескольких хостов это не покрывает. Основание: sqlite.org/whentouse.html, sqlite.org/wal.html и synchronous pragma. Код реализации пока не менялся.
